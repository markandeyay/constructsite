# WP-10: Scroll choreography assembly

Claimed 2026-09-18T02:12:43Z. Owns exactly one thing: the reserved region in
`src/main.ts` delimited by the `WP-10` markers.

---

## 1. What was written

The single `gsap.matchMedia()` block required by spec section 6.4, inside the
reserved region in `boot()`.

```ts
const mm = gsap.matchMedia();
mm.add(MQ_DESKTOP_MOTION, () => {
  const cleanups: Array<() => void> = [];
  const collect = (r: void | (() => void)) => { if (typeof r === 'function') cleanups.push(r); };
  collect(hero.initScrub());       // 01
  collect(how.initScrub());        // 03, the only pin on the page
  collect(structure.initScrub());  // 06
  return () => { for (const fn of cleanups) fn(); };
});
```

### The query

`MQ_DESKTOP_MOTION`, imported from `src/core/motion.ts`, never retyped. Its
value is `(min-width: 901px) and (prefers-reduced-motion: no-preference)`. One
query carrying both gates: the 901px width gate from spec section 5.4 and the
reduced-motion gate from spec section 13.1, which requires pins and scrubs to
be skipped entirely under reduced motion. Not split into two queries.

### Which sections are called, and which are not

Verified by grepping for a real export rather than following spec section 6.4's
seven-call example:

```
src/sections/hero.ts:379:      export function initScrub(): void
src/sections/how.ts:399:       export function initScrub(): () => void
src/sections/structure.ts:209: export function initScrub(): void | (() => void)
```

Those three and no others. `problem.ts`, `outputs.ts`, `validation.ts`,
`traction.ts`, `contact.ts`, `header.ts` and `footer.ts` export no `initScrub`.
Spec section 6.4 lists `initProblemScrub`, `initOutputsScrub`,
`initValidationScrub` and `initTractionScrub`; four of those have no counterpart
in the built code and are not imported or called. This is recorded as an
observation, not a spec challenge: the spec block is an illustrative example of
the ordering rule, and the rule is what was implemented.

Order is document order: 01, 03, 06. That ordering is the whole point of the
package. ScrollTrigger measures start positions at creation time, so a trigger
created before an earlier one measures against a document that does not yet
contain the earlier pin spacer, which yields a stale start and a visible
teleport.

### Cleanup

Two of the three return a cleanup (`how` and `structure`; `hero` deliberately
returns nothing, its motion being declarative parallax). They are collected and
a single function calling all of them is returned from the matchMedia callback,
which registers it as the matchMedia cleanup. GSAP runs it when the query stops
matching.

### No new motion

No ScrollTrigger is created by WP-10 itself. No fourth motion type. Spec
section 6.2 permits reveal, scrub and state, and nothing was added.

## 2. The debug global, stated plainly

**A debug global IS present in the shipped production bundle, and it is
opt-in.** It attaches nothing unless the URL carries `st-debug`:

```ts
if (location.search.includes('st-debug')) {
  (window as unknown as Record<string, unknown>).__WP10 = { gsap, ScrollTrigger };
}
```

A normal visitor at `https://<host>/` gets an untouched `window`: no `__WP10`
property is created, because the branch never runs. The cost in the bundle is
one string comparison and one object literal. It exists so the verification in
section 4 below could be measured against the real production build rather than
asserted, and so a later package (WP-15, WP-17) can re-measure the same way.
Removing it is a two-line deletion inside the WP-10 region if the orchestrator
would rather ship nothing at all.

## 3. The one line written outside the reserved region

An ES import declaration cannot live inside a function body, and the reserved
markers sit inside `boot()`. Spec section 6.4 and contract C2 require the query
to come from `core/motion.ts` rather than being retyped as a literal. So one
new line was added next to the existing motion import:

```ts
import { MQ_DESKTOP_MOTION } from './core/motion';
```

No existing line in `main.ts` was edited. The CSS imports, the section imports,
the `mount()` calls, `initMotion()`, `initScroll()`, the `document.fonts.ready`
refresh and the WP-15 region are all untouched.

## 4. Verification, measured

Method: `npm run build` (production), served by `vite preview` on port 4310,
driven by Playwright Chromium against `http://localhost:4310/?st-debug`.

Scroll is driven with **real wheel events**, not `window.scrollTo`. A first
attempt used `window.scrollTo` and produced a clean-looking but worthless
result: Lenis owns the scroll position and reverts a programmatic jump on the
next frame, so `scrollY` never left 0 and every sample was identical. The wheel
path is the path a user takes and is the only honest way to measure this.

### 4.1 ScrollTrigger table at 1440x900

| # | `vars.trigger` | start | end | distance | pin | scrub |
|---|---|---|---|---|---|---|
| 0 | `#how` | 1631 | 6131 | 4500 | `.sec-how__inner` | 1 |
| 1 | `#structure` | 8150 | 9943 | 1793 | none | 1 |

Total triggers: 2. Pinned triggers: 1. `hero.initScrub()` creates none by
design, so two triggers for three calls is correct.

**Overlapping pin ranges: none.** There is exactly one pinned trigger on the
page, so an overlap is not merely absent, it is not constructible. The only
other trigger starts at 8150, which is 2019px clear of the pin's end at 6131.
Spec section 19's checkbox is satisfied.

Note on run-to-run variation: an earlier run of the same build measured the pin
at start 1748 / end 6248. Absolute start positions shift by roughly 100px
between runs because the plasmid map mounts in an idle callback and fonts settle
asynchronously, which is exactly why `main.ts` refreshes on
`document.fonts.ready`. The pin **distance** is 4500 in every run.
