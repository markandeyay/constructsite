## Which POST path worked

**The primary path: `application/x-www-form-urlencoded`.** A plain `fetch` with
a `URLSearchParams` body reached the deployed Apps Script web app and the
`{"ok":true}` JSON read back normally. No preflight, no CORS problem, no
redirect problem, and `mode: 'no-cors'` was never needed or used. The observed
request header was `content-type: application/x-www-form-urlencoded;charset=UTF-8`.

The documented `text/plain;charset=utf-8` fallback is implemented but was not
needed for delivery. It is exercised by the failure-path test, which confirms it
fires exactly once and only when the first attempt is unreachable. A response
that answers `ok: false` is treated as final and is never retried, so a rejected
send can never become a double send.

## Decisions

1. **Rejection is not retried.** The spec's fallback exists for a transport
   problem. Retrying a relay that answered `ok: false` (for example the 20 second
   per-address rate limit) would risk a duplicate email, so the client only falls
   back when the first attempt produced no readable verdict.
2. **The pending ellipsis animates opacity, not text.** The status line is an
   `aria-live` region, so animating its text content would make a screen reader
   re-announce on every tick. Three dot spans are written once and only their
   opacity moves. Both `.no-motion` and the reduced-motion media query settle
   them.
3. **The form carries `novalidate`.** Native bubble validation cannot be styled,
   is not announced through the status line, and would pre-empt the spec 10.7
   `aria-invalid` behaviour. Validation is done in code and mirrors the server
   rules exactly.
4. **`form.noValidate` plus `required` and `aria-required`** keeps the semantics
   for assistive technology while the code owns the messaging.
