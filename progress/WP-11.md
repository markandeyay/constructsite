## 1. The CLS bug sweep

### 1.1 The bug class, restated and reproduced

`main.ts` is a deferred module, so Chromium paints the empty `<section>` shells
from `index.html` before any `mount()` runs. A section root class such as
`.sec-hero` is added by that `mount()`. If the CSS behind that class changes
padding, margin or display relative to the shared shell rhythm in `layout.css`,
the page reflows after first paint and spends CLS against a budget of exactly
0.00 (spec section 12).

The first thing this package did was build a harness that can actually see the
defect, because a harness that reports 0.0000 on a broken page proves nothing.
`qa/wp11-cls.mjs` registers a buffered `layout-shift` observer before any page
script runs, delays the entry chunk by 700ms so the empty shells are guaranteed
to paint first, and can splice a candidate rule into the real stylesheet
response so the rule is present at first paint rather than injected afterwards.

Control experiment, with `.sec-hero { padding-block: 200px; }` spliced in:

### 1.5 One real CLS finding, and it is NOT the bug class

After a stepped scroll sweep, and only at and above 901px with motion allowed,
CLS is non-zero:

| Viewport | CLS after a stepped sweep | CLS after a smooth sweep |
|---|---|---|
| 901x900 | 0.0197 | not run |
| 1024x768 | 0.0316 | 0.0001 |
| 1440x900 | 0.0168 | 0.0001 |
| 1920x1080 | 0.0132 | 0.0000 |

Under reduced motion it is 0.0000 at every width, and below 901px it is 0.0000
at every width, because the pin does not exist there.

The single dominant source, with its own reported rectangles at 1440x900:

```
div.sec-how__vis.sec-how__vis--on
  previousRect  x=262  y=0    w=249  h=81
  currentRect   x=739  y=321  w=536  h=83
```

That is not a root padding override. It is section 03's diagram: in the stacked
variant `.sec-how__vis` is in normal flow, and `.sec-how--staged .sec-how__vis`
makes it `position: absolute` at `inline-size: 48%` on the right. The staged
class is added by `initScrub`, so the element is laid out once in the stacked
position and then moved. The move is only *recorded* when the element later
stops being `visibility: hidden` during the scrub, which is why a smooth sweep
mostly misses it and a stepped one catches it.

**This is outside the orchestrator exception**, which covers padding, margin and
display on a section ROOT, so nothing here was changed. The fix belongs to
WP-09c and is the same fix the exception describes: move the staged geometry out
of the `.sec-how--staged` dependency and into the
`@media (min-width: 901px) and (prefers-reduced-motion: no-preference)` query on
its own, so the absolute positioning applies at first paint and the class is
left to carry only the JS driven state. Logged in `PROGRESS.md`.

### 2.3 The fix

Neither `--t-hero` nor the 55/45 split was touched, and nothing in WP-09a's
block was edited. At and above 901px only:

- `#hero { padding-block-start: clamp(var(--sp-8), 6vh, var(--sp-12)); }`
  The rule is written against the SHELL, not against `.sec-hero`, precisely
  because of section 1 above: the shell exists in `index.html` and is painted
  from the first frame, so the shorter lead-in is never a post-paint reflow.
  Measured CLS with the rule in place is 0.0000 at every width in both modes.
  The closing padding is untouched, so the gap between the hero and section 02
  keeps the shared rhythm.
- `.sec-hero__lede`, `.sec-hero__actions` and `.sec-hero__status` each drop one
  spacing step (`--sp-6` to `--sp-4`, `--sp-8` to `--sp-6`, `--sp-6` to

  they cannot shift anything already on screen. `.sec-hero__title`'s margin is

### 2.5 The honest caveat: the fallback font

`font-display: optional` never swaps, so a visitor whose webfont does not arrive
inside the block period sees Georgia for the whole session. All four faces are
`rel="preload"` in `index.html`, so that is the rare case, but it is not
impossible. Measured with the font files aborted at the network, before this
package's rules:

| Viewport | headline lines | status bottom | fold |
|---|---|---|---|
| 375x812 | 6 | 769 | fits |
| 1024x768 | 5 | 814 | over by 46 |
| 1440x900 | **6** | 1093 | over by 193 |
| 1920x1080 | 6 | 1113 | over by 33 |

This package's rules recover about 96px of that, which fixes 1024 and 1920 and
leaves 1440x900 roughly 100px short in the fallback case. Closing the rest would
need either a smaller `--t-hero` or a wider copy column, and both are fixed by
the spec, so it is recorded here rather than quietly worked around. Georgia is
substantially wider than Instrument Serif at the same size, which is the whole
of the difference.

## R3. The cold load webfont question, answered

**The webfont wins on a cold load. Every time, on every profile tested. The

### R3.1 Two measurement traps, named first

`document.fonts.check()` is not a sufficient answer: under `font-display:
optional` a face that arrives after the block period still ends up loaded, so
`check()` reports true while the page stays painted in the fallback for the rest
of the session. The reliable discriminator is the RENDERED headline.

The second trap is that the deployed build walks into it. Production still
carries the old `size-adjust: 135.09%`, which was chosen precisely to match
Georgia's advance width, so on production Instrument Serif and Georgia render
IDENTICALLY: title height 581 at 1440x900 either way, measured with the font
files served and then with them aborted. On production the rendering test is
therefore degenerate and cannot answer the question on its own. On the current
build the two separate cleanly:

| | 1440x900 | 375x812 |
|---|---|---|
| Instrument Serif | titleH 465, 5 lines | titleH 245, 5 lines |
| Georgia fallback | titleH 581, 6 lines | titleH 306, 6 lines |

So the rendering evidence is taken from the current build, and the network
evidence from the real deployment. Both point the same way.

Every run is a brand new browser context, so the HTTP cache, the font cache and

## R4. The reduced motion page level CLS: could not reproduce

The orchestrator reported 0.3552 / 0.2797 / 0.2222 / 0.1875 at 901x900, 1024x768,
1440x900 and 1920x1080 under reduced motion, a single entry sourced at BODY, not
reproducing with motion allowed. WP-15 owns diagnosing it. This package could not
reproduce it on the current build and tried the following, each at those four
widths, each reading 0.000000:

- reduced motion set at context creation, entry chunk delayed 700ms, stepped
  sweep, which is the standard run here.
- the same with a full page screenshot taken mid run, on the theory that
  Playwright's full page capture resizes the viewport and moves BODY once.
- the same with a viewport screenshot.
- loading with motion allowed, sweeping, then switching to reduced motion with
  `page.emulateMedia` after load, on the theory that reverting the matchMedia
  block removes the pin spacers and shrinks the document. The document height
  does drop sharply, 11510 to 8144 at 901x900 and 13101 to 8802 at 1920x1080,
  and yet no layout shift is recorded, because the change lands below the fold
  while the page is scrolled to the top.

Two leads for WP-15, since a BODY sourced value that scales inversely with
viewport height is a strong hint. First, a layout shift score is the moved
fraction of the viewport, so 0.2222 at 1440x900 is the whole document moving
roughly 200px in one frame, and the document does shrink by about 3300px when the
