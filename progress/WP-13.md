## 1. Deliverable 1: `public/favicon.svg` (the blocking gate)

### The failure that was blocking

`index.html` has always carried `<link rel="icon" href="/favicon.svg">`, but the
file did not exist. Under `vite preview` a missing public file does not return a
literal 404: it falls through to the SPA fallback and returns `200 text/html`,
which the browser then fails to decode as an image. That decode failure is the
console error WP-09a saw, and spec 16.6 makes zero console errors a hard gate on
every QA script. On Vercel the same link is a real 404.

Measured, on the built `dist/` served at `http://localhost:4713`:

```
BEFORE (behaviour of any absent public file, measured against /favicon-absent.svg)
  HTTP/1.1 200 OK
  Content-Type: text/html          <- not an image
  img.naturalWidth = 0             <- browser cannot decode it

AFTER (/favicon.svg, the file this WP shipped)
  HTTP/1.1 200 OK
  Content-Type: image/svg+xml
  Content-Length: 923
  img.naturalWidth = 32, naturalHeight = 32
```

Full-page load plus scroll sweep, at 375x812, 900x1200 and 1440x900, with the
declared icon href explicitly fetched by the page on each run:

```
[375x812]   icon link fetched by page: {"/favicon.svg":200}
            console errors: 0   page errors / rejections: 0   failed requests: 0
[900x1200]  icon link fetched by page: {"/favicon.svg":200}
            console errors: 0   page errors / rejections: 0   failed requests: 0
[1440x900]  icon link fetched by page: {"/favicon.svg":200}
            console errors: 0   page errors / rejections: 0   failed requests: 0
```

The gate is unblocked.

### What it is

Spec 14: a simple circular ring with three arc segments in the feature colours,
which reads as a construct map at 16px. Spec 2.4 bans DNA helix clip art, so
there is none.

Hand written, 923 bytes, `viewBox="0 0 32 32"` so it lands on exact pixel
boundaries at 16px and at 32px. One backbone ring at `stroke-width 1.5` in
`#C9C5BD` (`--rule-strong`), three feature arcs at `stroke-width 4`, built from
`stroke-dasharray` / `stroke-dashoffset` on three concentric circles rather than
from arc paths, because dash arithmetic is exact and arc flags are not.

Colours are the spec 5.2 feature tokens as hex literals, since an SVG file
cannot resolve CSS custom properties from the page:

| Arc | Token | Hex | Share of circumference |
|---|---|---|---|
| 1 | `--feat-promoter` | `#2E6F95` | 30% |
| 2 | `--feat-cds` | `#1F6B4A` | 26% |
| 3 | `--feat-marker` | `#8A5E12` | 24% |

Three gaps of 6.67% each. `r = 11`, circumference `2*pi*11 = 69.115`, so the
dash lengths are 20.73, 17.97 and 16.59 with offsets 0, -25.34 and -47.92. The
group is rotated -90 degrees so arc 1 starts at twelve o'clock. Butt caps, not
round: round caps close the gaps to mush at 16px.

### Checked at 16px, not assumed

Rendered through Chromium at a true 16x16 raster and then upscaled with
nearest-neighbour to inspect the actual pixels. At 16px all three arcs stay
distinct, all three gaps stay open, and the ring stays a ring. The 1.5-unit
backbone drops below one device pixel at 16px and reads as a faint tint, which
is the intended behaviour: it carries the map at 32px and above and does not
compete at favicon size. Also checked at 64px.

One real bug was caught and fixed by rendering rather than assuming: the first
version put the literal token names in an XML comment, and `--feat-*` contains a
double hyphen, which is illegal inside an XML comment. Chromium refused to parse
the whole file. The comment is now written without a double hyphen.

### The framing problem, and how it was solved

A 1200x630 viewport is 630px tall and the hero does not fit in it. Captured that
way, the headline and the plasmid map are both sliced in half. This is the same
underlying fact as the G1 risk WP-09a filed: the display serif headline runs
many lines at wide viewports.

The card is therefore rendered at **1880x987**, which is the identical 1200:630
aspect ratio, with `deviceScaleFactor = 1200/1880 = 0.6383`, so Chromium
rasterises straight to exactly 1200x630 in one pass. It is still a real
screenshot of the real hero at the required aspect ratio, just at a larger
effective CSS width. Candidates at 1200x630, 2000x1050, 1800x945 and 1880x987
were all rendered and compared; 1880x987 is the one where the whole hero fits
with margin (hero bottom 1056.97 against a 987 viewport, with the status line
clear of the bottom edge) and the type is still legible at card size.

### Settling the frame

- `reducedMotion: 'reduce'` on the browser context. Spec 13.1 makes reduced
  motion a contract: every reveal renders in its settled state and the hero
  plasmid map renders fully drawn. That gives a deterministic frame instead of
  racing the load timeline.
- Awaited `document.fonts.ready`, so the display serif is the real Instrument
  Serif and not the Georgia fallback baked in.
- Awaited the plasmid map actually finishing, by polling for an SVG inside
  `.fx-plasmid` carrying more than ten drawn nodes, rather than a fixed sleep.
  Spec 8.6 mounts seqviz in an idle callback, which has no guaranteed
  wall-clock time. A 3s settle follows.
- The capture retries up to three times. This was not theoretical: one run out
  of six timed out waiting for the seqviz mount, so the retry is load bearing.
- Zero console errors during the capture run.

### Regenerate it when the demo data becomes real

The map in the card is the `_TODO` placeholder payload WP-06 logged under
Blocked (`pCON-DEMO-01`). That is correct today, because the card is by
definition a render of the site as it stands. **When a real construct export
replaces `public/data/demo-plasmid.json`, regenerate this card**, or it will
show a construct the site no longer shows. The capture script is reproducible
from the parameters above: viewport 1880x987, deviceScaleFactor 1200/1880,
reduced motion, wait on `document.fonts.ready` and on the map, clip
`{x:0, y:0, w:1880, h:987}`.

No banned string appears anywhere in the PNG bytes, image metadata included.

## 3. Deliverable 3: the `<head>` metadata

**`index.html` was not edited.** WP-01 authored the head exactly as spec 14
specifies it, using the `%SITE_ORIGIN%` token, and every user-facing string in
it already matches `copy.meta` verbatim. Contract C8 gives WP-13 permission to
adjust it; nothing needed adjusting, so nothing was touched. `git status` shows
`index.html` unmodified.

Verified in the **built** `dist/index.html`:

```html
<title>Construct: validated genetic designs from plain English</title>
<meta name="description" content="Construct turns plain-English intent into validated, ready-to-build genetic designs. Plasmids, viral vectors, mRNA, antibodies, and CAR-T constructs, checked by a deterministic validation engine." />
<meta property="og:title" content="Construct" />
<meta property="og:description" content="Describe what you want to build. Get a design you can order." />
<meta property="og:image" content="https://constructsite-nine.vercel.app/og-card.png" />
<meta property="og:url" content="https://constructsite-nine.vercel.app/" />
<meta property="og:type" content="website" />
<meta name="twitter:card" content="summary_large_image" />
<link rel="icon" href="/favicon.svg" type="image/svg+xml" />
```

- All nine spec 14 tags present.
- `og:image` is an **absolute** URL, per the spec 14 warning that Slack and
  several other scrapers will not resolve a root-relative path and will silently
  fail to render the card. Asserted by regex against the built HTML.
- `og:url` is absolute.
- `%SITE_ORIGIN%` appears **nowhere** in `dist/` after the build. Grepped the
  whole output directory, not just `index.html`.
- The host is not hard-coded anywhere by this WP. It comes from the single
  `SITE_ORIGIN` constant in `vite.config.ts` through the `transformIndexHtml`
  plugin, per contract C4, so a custom domain stays a one-line change.
- Every user-facing string checked programmatically against `src/content/copy.ts`:
  `title`, `description`, `ogTitle` and `ogDescription` all appear verbatim in
  `copy.meta`. No new marketing copy was authored.
- No em dash in the head.

### Content safety (Appendix B)

The title and og:description are the approved strings already in `copy.ts`.
"Construct: validated genetic designs from plain English" and "Describe what you
want to build. Get a design you can order." assert no number, no user count, no
partnership, no funding, no wet-lab claim and no clinical status. The
description names output categories as platform capabilities, which is exactly
what the Appendix B "Output breadth" row allows.
