## 2. The module, `src/fx/viewer3d.ts`

Contract C9 is exact:

```ts
export function mountViewer3d(el: HTMLElement): Promise<{ setZoom(p: number): void; destroy(): void } | null>;
```

Behaviour worth knowing if you are WP-09f or WP-10:

- **The promise settles immediately.** It resolves `null` when the still was
  rendered, and otherwise resolves the handle straight away, before 3Dmol has
  been imported. The import and first render happen later, on approach. Any
  `setZoom` call made before then is buffered and applied the moment the viewer
  exists. An implementation that only resolved on approach would have left
  WP-09f awaiting a promise that never settles until the user scrolls.
- **No ScrollTrigger is created here.** `setZoom(p)` maps `0..1` to camera zoom
  and WP-10 drives it from the single `matchMedia` block (spec section 6.4).
- **DOM.** The module adds `.fx-viewer3d` to the element it is given and appends
  either `div.fx-viewer3d__stage` (which 3Dmol fills with its canvas) or
  `img.fx-viewer3d__still`. It appends nothing else and queries nothing outside
  its own element, so the attribution line (`structure.pdbcredit`, WP-04's
  string, rendered by WP-09f) cannot collide with it.

### Palette

Hex literals, because 3Dmol runs in WebGL and cannot resolve CSS custom
properties. They are kept in sync with `tokens.css` by hand and the file says so
in a comment.

| `atom.ss` | Hex | Token |
|---|---|---|
| `h` (helix) | `#1F6B4A` | `--accent` |
| `s` (sheet) | `#2E6F95` | `--feat-promoter` |
| `c` (coil) | `#656E77` | `--ink-faint` |
| background | `#F2F0EC` | `--paper-sunk` |

3Dmol sets `atom.ss` to the single characters `h`, `s`, `c`, never
`helix`/`sheet`/`coil`. The `colorfunc` keys on the single characters and falls
back to the coil grey. No spectrum, no rainbow, no coloured lights, default
lighting, `antialias: true`, cartoon with `thickness: 0.4` and `arrows: true`,
then `zoomTo()` and `render()`.

Confirmed from rendered pixels, not from the source: the eight most common
colours in the live canvas are the paper-sunk background and shaded variants of
the blue sheet and grey coil. No saturated or out-of-palette hue appears.

### Motion, spec section 7.6

- Auto-rotation is `viewer.rotate(0.2, 'y')` once per animation frame. `rotate`
  re-renders, so there is no second `render()` per frame.
- Drag is 3Dmol's own handler. A `pointerdown` on the stage stops the loop, and
  `pointerup`/`pointercancel` on `window` (so a release outside the canvas still
  counts) sets a 4,000 ms resume time.
- Under reduced motion the loop is never started, so nothing auto-rotates, and
  the viewer stays draggable because 3Dmol owns that interaction.
- The rAF loop stops when the element leaves the viewport (its own
  `IntersectionObserver`), when the tab is hidden, and on `destroy()`.
- `setZoom(p)` is absolute, not accumulating: the target factor is
  `0.78 + p * (1.55 - 0.78)` relative to the `zoomTo()` fit, and the module
  applies `target / alreadyApplied` so repeated scrub calls cannot drift.

### Lazy loading, spec sections 9.5 and 12

One `observeOnce(el, load, '150% 0px 150% 0px')` from `core/observe.ts`. The
margin is 1.5 viewport heights above and below, because the section can be
approached from either direction. `await import('3dmol')` happens inside that
callback and nowhere else.

### Fallback, spec section 9.4

`!WebGLRenderingContext` (or a context probe that fails) or
`window.innerWidth < 720` renders the still and returns `null`, and 3Dmol is
never requested. A failed import or a failed structure fetch also swaps in the
still rather than leaving a blank box, with one `console.warn` (a warning, not
an error, so the zero-console-errors gate still holds).

### Accessibility, spec section 13.2

The stage carries `role="img"` plus an `aria-label` describing the barrel, the
central helix and the colour coding in words. The still carries the same
description as its `alt`. Neither is empty, neither is a filename.

These two strings live in `viewer3d.ts` rather than `copy.ts`, because the
frozen `copy.structure` shape in contract C3 has no alt key and `copy.ts`
belongs to WP-04. Noted as a cross-WP line in `PROGRESS.md`.

### Layout stability

`.fx-viewer3d` reserves `aspect-ratio: 4 / 3` and the still carries explicit
`width="1200" height="900"`, so neither the canvas nor the image can shift
layout. The still is `loading="eager"`, because the structure section is
measured by a scroll scrub and a late image inside a measured section produces
stale triggers (spec section 7.3).

# WP-07-fix: the section 12 frame budgets

Claimed 2026-09-18T04:41:13Z. Owns `src/fx/viewer3d.ts` and the `WP-07` block in
`src/styles/sections.css`. **Only `src/fx/viewer3d.ts` was changed.** The CSS
block was not touched, and no file outside this package was edited.

Summary line 1: one 3Dmol render of the 898x673 stage cost roughly 330ms at 6x
CPU throttle, so no amount of rotating less often could meet a 200ms long-task
budget; the viewer now renders at the resolution the device is measured to
afford, and every long task attributable to the viewer during a scroll sweep is
gone except the one-time init that section 12 already permits.

Summary line 2: the janked-frame budget cannot be assessed on this machine right
now, because a blank scrolling control page measured with the same harness in the
same minutes reads 56% jank against the 2% budget; every number below is printed
next to that control.

## 1. What the previous state actually was

The working tree was not the original WP-07. Commit `4871b1c` had already landed
a rotation throttle into `viewer3d.ts` (rotate on a 50ms interval at a
time-derived angle, suspend while the page is scrolling, throttle the zoom
render), and the uncommitted working tree added `upscale: false` plus a
`__wp07probe` debug line left on `window`. The probe was removed.

The true "before", and the state WP-15 measured, is `cf550f4`:
`viewer.rotate(0.2, 'y')` once per animation frame, `applyZoom` calling both
`zoom()` and `render()`, and no `upscale` override. Every BEFORE number below was
taken against a build of exactly that file, recovered with
`git show cf550f4:src/fx/viewer3d.ts`.

## 2. Why rotating less often could not have worked

Measured with the viewer parked on the structure section, 1440x900, 6x CPU
throttle, an 8 second window, sourcemapped CPU profile:

| | canvas backing | renders in 8s | long tasks over 200ms | longest task |
|---|---|---|---|---|
| original (`cf550f4`) | 1796x1346 | 11 | **11 of 11** | 892ms |
| original, repeat | 1796x1346 | 11 | **11 of 11** | 801ms |

Every single render was itself a long task of 685ms to 892ms. The profile names
the cost precisely: `transferToImageBitmap` at 10,525ms of a 10,843ms window.
3Dmol renders into a singleton `OffscreenCanvas` and copies the result onto the
visible canvas with `transferToImageBitmap` / `transferFromImageBitmap` on every
render, and that copy blocks the main thread in proportion to pixel count.

So the render *rate* was never the binding constraint. One render was already
four times the budget. The lever is pixels.

## 3. What changed, and what each lever is worth

Four changes, all in `src/fx/viewer3d.ts`.

**(a) `upscale: false` on `createViewer`, kept from the working tree and verified
rather than trusted.** 3Dmol defaults `upscale` to the `antialias` setting, and
`Renderer.setSize` then forces `devicePixelRatio` to 2.0 on any display below 2x.
On a 1x display that renders four times the pixels for a supersampling nicety on
top of the antialiasing the context already performs. Antialiasing stays on, as
section 9.2 requires. Measured: backing store 1796x1346 to 898x673, and
`transferToImageBitmap` over an 8s parked window from 10,525ms to 3,816ms.

**(b) Adaptive render resolution.** 898x673 still cost roughly 330ms a render at
6x throttle. The viewer now times every render it issues. After two consecutive
renders over 80ms it steps the backing store down via `setWidth` / `setHeight`,
which set the viewer's dimensions independently of the container and do not
render, through 1.0, 0.68, 0.5, 0.36, choosing in one move the largest step whose
estimated cost fits, since cost tracks area. The canvas is then stretched back to
100% of its box by inline CSS, so the reserved `aspect-ratio: 4 / 3` box, the
layout and the CLS budget are untouched. The ladder only steps down.

This is device-adaptive quality, not a harness trick: on any machine where a
render is cheap the ladder never leaves step 0 and the image is unchanged. Below
720px the viewer is never loaded at all, so the only devices that reach this code
are desktops with WebGL.

**(c) 3Dmol's duplicate observers are disconnected.** `GLViewer` attaches a
`ResizeObserver` **and** an `IntersectionObserver` to the element it is given, and
both call its `resize()`, which re-derives the buffer from the container and
renders. This module already observes intersection and resize itself, so those two
are duplicates that spend a full-resolution render every time the section scrolls
into view, and they also silently undid the step in (b). They are disconnected
behind `typeof` guards and this module drives both events. The scale is
additionally re-asserted before each render, which is two property reads when the
ladder is at step 0.

**(d) Render pacing.** After a render costing C, the next is not allowed for
`2 * C`, capped at 400ms. At 5ms a render, which is a real desktop, that is a 10ms
wait and nothing is throttled at all. It bounds the viewer's share of the main
thread on any device.

Kept from the working tree, and still correct: the 50ms rotation interval with a
time-derived angle (20 steps a second at 0.6 degrees is the same visible speed as
60 steps at 0.2, which is the rate section 7.6 specifies), the suspension of
rotation while the page is actively scrolling (the scrub already owns the camera,
so a rotation step underneath it is invisible, and it is the one that costs two
renders in one frame), and the coarser zoom render cadence while scrolling.

## 7. PART 2: what janks at 375px, where 3Dmol never loads

It is not JavaScript, and it is not this module.

A sourcemapped CPU profile of the 375x812 sweep, after build, 6x throttle, over a
9.5 second sweep:

```
LONG TASKS OVER 200ms IN SWEEP: 0     in every 375 profile run

TOP SELF TIME IN SWEEP
  4656ms  (program)            browser style, layout, paint and composite
  2668ms  (idle)
   956ms  scrollTo             native, called by Lenis every frame
   318ms  (garbage collector)
   212ms  lenis
    23ms  core/scroll.ts:80 broadcast
```

Every line of this site's own code together accounts for well under 100ms across
the whole sweep. `(program)` alone is 49% of the sweep's wall clock. There is
nothing for a JavaScript optimisation to remove.

**What that `(program)` time is spent on is rasterising the hero plasmid map.**
Measured by hiding exactly one element just before the sweep, `visibility: hidden`
on `.fx-plasmid`, which removes its paint while leaving its layout, its DOM and
its script untouched. Two pairs, alternated:

| | `(program)` self time | janked | sweep coverage |
|---|---|---|---|
| as shipped, pair 1 | 4500ms | 11.45% | 85.7% |
| hero map paint removed, pair 1 | **2452ms** | 5.63% | 100% |
| as shipped, pair 2 | 3937ms | 8.34% | 71.4% |
| hero map paint removed, pair 2 | **1762ms** | 7.17% | 100% |

Removing the paint of one element halves the browser's per-frame cost across the
whole sweep, and is the difference between a sweep that completes inside 8 seconds
and one that does not. A "hide all of `main`" floor run reads 2129ms of
`TaskDuration` against 5285ms as shipped, and hiding only the hero map reaches
2872ms, within 740ms of that floor.

It is paint, not layout and not script: `visibility: hidden` changes neither of
the latter. It is not parallax: `core/motion.ts` gates the parallax subscriber at
`PARALLAX_MIN_WIDTH = 901`, so at 375 no `data-depth` element is transformed at
all.

**The file is `src/fx/plasmid.ts` (WP-06), with the container markup in
`src/sections/hero.ts` (WP-09a) and the `.fx-plasmid` styles in WP-06's block in
`sections.css`. None of those belong to this package and none of them were
edited.** A `## Cross-WP requests` line is appended to `PROGRESS.md`.

The fix is to stop the browser re-rasterising a large static SVG on every scroll
frame. The candidates are `contain: paint` on `.fx-plasmid`, giving it its own
composited layer with `will-change: transform`, or `content-visibility: auto` with
a matching `contain-intrinsic-size` so it is not rastered while off screen, applied
after the section 8.4 draw animation has finished so the animation is unaffected.
**Which of those three works is not established here.** They were each measured
three times and the ordering did not reproduce under the machine noise described in
section 5. The cause is measured; the remedy is not, and it should be chosen by
re-running that A/B on a quiet machine.
