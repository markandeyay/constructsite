and `qa/perf.mjs`. Used the narrow orchestrator exception on `src/fx/plasmid.ts`
for the seqviz import and nothing else.

## 2. The bundle, before and after

The headline problem was an initial chunk of 212.79 kB gzipped against a 200 KB
budget. The fix is one line: seqviz's value import became a dynamic import.

| Chunk | Before | After |
|---|---|---|
| entry, `assets/index-*.js` | 647.80 kB raw, **212.79 kB gzip** | 184.04 kB raw, **67.57 kB gzip** |
| seqviz plus React and react-dom, `assets/index.browser-*.js` | inside the entry | 462.35 kB raw, 142.68 kB gzip, loaded on demand |
| commonjs helpers | inside the entry | 731 B raw, 407 B gzip, loaded with the seqviz chunk |
| 3Dmol, `assets/3Dmol-*.js` | 587.80 kB raw, 169.76 kB gzip, already split | unchanged, still split |
| CSS | 5.94 kB gzip | 5.77 kB gzip |

**Why this is legitimate and not a budget dodge.** Section 12 says seqviz is
above the fold so it cannot be deferred the way 3Dmol is. That sentence is about
deferring the MAP, not the IMPORT. Section 8.6 already mounts the map after first
paint inside `requestIdleCallback`, with a `setTimeout(0)` fallback for Safari,
precisely because seqviz's first render is the heaviest operation on load. The
import now happens inside that same idle callback. The map mounts at the same
moment, in the same order, draws the same animation, keeps the same tooltip
behaviour, the same reduced-motion guarantee and the same `aria-label`. What
changed is that seqviz, React and react-dom are no longer fetched, parsed and
evaluated before the hero can paint.

Measured at 1440x900 with 6x CPU throttle: the seqviz chunk is requested at
881ms, after first paint at 124ms and after first contentful paint at 504ms, and
the hero map appears at 1284ms.

**The same change rescued three other budgets**, which is the strongest evidence
that it is a real improvement rather than accounting. Same tree, same machine,
same Lighthouse invocation, the only difference being the static import:

| | Before, static import | After, dynamic import |
|---|---|---|
| Lighthouse Performance, mobile | 61, 67 | 99, 97, 97 |
| Largest Contentful Paint | 5294ms, 5261ms | 2205ms, 2158ms, 2400ms |
| First Contentful Paint | 4270ms, 4280ms | 1327ms, 1259ms, 1210ms |
| Total Blocking Time | 368ms, 191ms | 35ms, 127ms, 116ms |
| Cumulative Layout Shift | 0 | 0 |

The budget was not raised. `qa/perf.mjs` still carries the section 12 numbers
exactly as WP-16 wrote them.

### 3Dmol is not in the initial bundle (section 12.1, section 19)

`dist/assets/index-ipcUBqs3.js` contains no 3Dmol code. The only match for
`createViewer` in it is WP-07's own call site inside the dynamic import
callback, and the only 3Dmol string is the chunk path in vite's dependency map.
Measured on the assembled page: at 1440x900 the 3Dmol chunk is first requested
at 11574ms, on approach to the structure section, and at 375x812 neither the
3Dmol chunk nor the 190 KB `gfp.pdb` is ever requested, with the WebP still
loading at 421ms instead. That reproduces WP-07's section 4.1 measurement
against the assembled build.

## 3. Cumulative Layout Shift, including the reported reduced-motion failure

CLS was reported to me as a page-wide failure of 0.3552 / 0.2797 / 0.2222 /
0.1875 under reduced motion at 901x900, 1024x768, 1440x900 and 1920x1080, with
BODY as the only source at 1440.

**It does not reproduce as a visitor experience, and I found what does produce
it.** Every measurement below sets reduced motion on the browser context BEFORE
navigation, which is how a real visitor arrives: the media query is already true
when the document loads, so the pins are never created and there are no pin
spacers to remove.

| Harness | Condition | Result |
|---|---|---|
| WP-11's `qa/wp11-cls.mjs`, entry chunk delayed 700ms, stepped sweep | 7 viewports x both motion modes, final build | 0.0000 in 14 of 14 |
| Same, against the pre-fix build | 7 viewports x both motion modes | 0.0000 in 14 of 14 |
| My own stepped-sweep harness | 901x900, 1024x768, 1440x900, 1920x1080, reduced motion, entry delay 0 and 700ms | 0.0000 in 8 of 8 |
| The `qa/perf.mjs` CLS pass, entry delayed, stepped sweep | 1440x900, 6x throttle | 0.0000 |
| Lighthouse mobile | 3 runs | 0 in 3 of 3 |

**What does reproduce it.** Loading with motion allowed, scrolling to 45% of the
document, and only then switching the browser to reduced motion:

| Viewport | document height before | after | CLS |
|---|---|---|---|
| 901x900 | 11510 | 7904 | **1.0000** |
| 1024x768 | 10589 | 7696 | **1.0000** |
| 1440x900 | 11816 | 8262 | **1.0000** |
| 1920x1080 | 13101 | 8562 | **1.0000** |

Killing the pins removes roughly 3,300 to 4,500px of pin spacer from a document
whose viewport is parked part way down, so everything visible jumps at once. The
source reported is whichever section is on screen, which at 1440 is
`section#structure`. That is the mechanism behind a large BODY-sourced entry, and
it is an artifact of changing the motion mode after the page has laid out with
pins. No visitor can be in that state. Verdict: **not a page defect. CLS is
0.00.**

The harness was validated against a known-bad control rather than trusted. With
`.sec-hero { padding-block: 200px; }` spliced into the real stylesheet response
so the rule is present at first paint, the same harness reads 0.1013 at 375x812
and 0.1164 at 768x1024 under reduced motion, reproducing WP-11's recorded control
numbers. A harness that reads 0.0000 on a known-bad page proves nothing, and this
one does not.

### One real but currently harmless shift source, for the record

`.fx-plasmid--mini` is added by `mountPlasmid` at mount time and is not in the
markup, and it narrows `max-inline-size` from 560px to 320px. Measured at
1440x900: the section 03 map box goes 560 to 320 and `#how` shrinks by 240px
after first paint. It scores 0.0000 today in every scenario I could construct,
because during a downward sweep the collapse happens above the viewport and
Chromium's scroll anchoring absorbs it. Measured directly: at the moment of the
collapse the scroll position itself moved from 3182 to 2942, which is scroll
anchoring compensating. It is a reservation that is not actually reserving, and
the fix is one class in the markup. Logged as a cross-WP request rather than
edited, since both candidate files belong to other packages.

## 4. The two budgets that are missed, and why

Both come from the same discovery, and it only became visible once the sweep
actually scrolled.

**The sweep never scrolled.** `qa/perf.mjs` drove the sweep with an in-page
`window.scrollTo` loop. Measured on this build at 1440x900 with 6x throttle, that
loop moved the page **12px out of 10,916px of scrollable document in 8 seconds**,
because Lenis owns the scroll and reverts a programmatic jump on the next frame.
The orchestrator recorded this trap from WP-10 and it applies directly here.
Every frame, jank and long-task number taken that way described a page that was
standing still: it read a median of 3.0ms and jank between 0.55% and 4.81% run to
run on an unchanged page, and it never loaded 3Dmol at all.

The sweep is now dispatched as real wheel events from the harness process, and
the script asserts afterwards that it reached the bottom (96.4% of the scrollable
distance in the recorded run), so it can never fail silently again.

**Against a sweep that really scrolls:**

- Median frame is **7.0ms**, comfortably inside the 12ms budget.
- Janked frames are **9.99%** against a 2% budget. Repeat runs: 6.45%, 10.95%,
  11.23%, 13.58%, 15.43%. Under reduced motion, where Lenis is not installed and
  no pin, scrub or auto-rotation runs, the same sweep reads **0.79%**.
- Long tasks over 200ms during the sweep: **4 remain** after the one permitted
  3Dmol exclusion, at 671ms, 394ms, 347ms and 320ms.

**Attribution, by CPU profile with sourcemaps rather than by reasoning.** Every
long task over 200ms inside the sweep resolves to `3Dmol.js:29795`, the viewer's
render, with 1115ms, 1266ms, 264ms, 490ms and 540ms of self time in five
consecutive tasks starting at approach+512ms, +2298ms, +3946ms, +4436ms and
+5094ms. The first cluster is the genuine one-time init: chunk evaluation, the
PDB parse in `getSinglePDB`, the first geometry build. The later ones are not
one-time. They are the continuous auto-rotation of spec section 7.6, which calls
`viewer.rotate(0.2, 'y')` once per animation frame, and each of those renders
costs hundreds of milliseconds at 6x CPU throttle.

Across the whole sweep the top self-time entries are `(program)` at 4815ms, which
is browser style, layout and paint, `3Dmol.js:29795` at 1797ms,
`gsap/Observer.js:120` at 1288ms, which is the wheel handler,
`3Dmol getSinglePDB` at 300ms and `core/scroll.ts:80 broadcast` at 255ms. Site
code other than the viewer is a small share of the total.

**Jank is not only 3Dmol.** Blocking the 3Dmol chunk entirely, so the viewer
falls back to the still, the same sweep still reads 13.58% and 6.45%. At 375x812,
where 3Dmol never loads and no pin or scrub exists, it reads 10.33%.

**A calibration control, so the number is never read without the condition that
produced it.** A plain 13,560px scrolling page served locally, swept the same
way, with the same flags and the same 6x throttle, reads median 17.1ms and
**0.00% jank**. The harness and this machine can measure 0.00%, so the 6 to 15%
is the page.

**What I did not do.** I did not relax the budget, widen the jank threshold, or
add a third exclusion. The 2% and the 20ms in `qa/perf.mjs` are exactly as WP-16
wrote them. The changes that would move these two numbers live in
`src/fx/viewer3d.ts` and in the motion stack, neither of which this package owns,
so they are written up as cross-WP requests with measurements attached and
nothing was edited.

One caveat on precision: 54 node and chrome processes belonging to sibling agents
were running during these measurements, and the run-to-run spread reflects that.
The direction is not in doubt, because the reduced-motion run and the control
page were measured on the same machine in the same minutes and read 0.79% and
0.00%.

## 6. What I changed

Three files, and nothing else in the repository.

1. **`src/fx/plasmid.ts`**, under the narrow orchestrator exception, seqviz
   import only. The value import `import { Viewer } from 'seqviz'` was removed
   and replaced by `const { Viewer } = await import('seqviz')` placed immediately
   after the existing `await afterFirstPaint()` inside `mountPlasmid`, which is
   the section 8.6 idle callback. The type import
   `import type { SeqVizProps } from 'seqviz'` stays, because a type import is
   erased at compile time and carries no runtime weight. A comment block at the
   top of the file records the change and the reasoning. **Nothing else in that
   file was touched:** not the mount timing, not the draw animation, not the
   tooltip behaviour, not the reduced-motion guarantee, not the `aria-label`.
2. **`src/main.ts`**, inside the reserved `WP-15` region only. One
   `performance.mark('wp15:boot-end')` and one
   `performance.measure('wp15:boot', ...)`, wrapped in try/catch, closing the
   synchronous boot window so a harness can name the boot cost rather than infer
   it from where long tasks happen to fall. Two User Timing calls, no listener,
   no timer, nothing per frame. `qa/perf.mjs` prints it: 450ms in the final run.
3. **`qa/perf.mjs`**, which this package is allowed to extend. Four changes, all
   corrections or additions, none of them a relaxed budget:
   - the sweep is driven by real wheel events and asserts it reached the bottom;
   - long tasks are judged over the sweep window, which is what section 12 says,
     with boot tasks printed under their own heading because their budget is
     Total Blocking Time;
   - the sweep starts when the page is quiet rather than after a fixed 2500ms,
     since at 6x throttle the one-time seqviz mount was often still running at
     2500ms and the sweep then measured boot;
   - a second pass measures CLS with the entry chunk delayed and a stepped sweep,
     which is WP-11's validated method, and fails on anything that does not round
     to 0.00.

## 7. Cross-WP requests, all measured, none edited

- **To WP-07 (`src/fx/viewer3d.ts`).** Auto-rotation calls
  `viewer.rotate(0.2, 'y')` once per animation frame, and a single 3Dmol render
  measures 264ms to 1266ms of self time at 6x CPU throttle. That is the whole of
  the remaining long-task failure: consecutive tasks of 362ms, 1781ms, 1645ms,
  475ms, 657ms and 619ms while the structure section is on screen. Suggested
  change, which keeps spec section 7.6's continuous rotation: skip the rotation
  frame while the page is scrolling (`core/scroll.ts` already broadcasts a signed
  velocity), or rotate on every Nth frame by a proportionally larger angle so the
  visible speed is unchanged and the render count drops.
- **To WP-09c (`src/sections/how.ts`), copied to WP-06.** The map container is
  built as `class="fx-plasmid sec-how__map"` and `mountPlasmid` adds
  `fx-plasmid--mini` at mount, which narrows the reserved box from 560px to 320px
  and shrinks `#how` by 240px after first paint. Adding `fx-plasmid--mini` to the
  markup makes the reservation honest. It scores 0.0000 today only because scroll
  anchoring absorbs it.
- **To WP-16 (`qa/perf.mjs`).** The four changes in section 6 are in your file.
  The measurement approach note at the top of the script was extended rather than
  replaced, and your vsync note is untouched and still printed on every run.
- **To WP-17.** `qa/perf.mjs` exits non-zero today on the two budgets in section
  4. That is the honest state of the page, not a harness failure, and the harness
  now proves that its sweep actually scrolled.
