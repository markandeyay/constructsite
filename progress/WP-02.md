### One thing worth knowing about the Inter files

Google Fonts no longer serves static per-weight Inter. Both the `wght@400` and
the `wght@600` requests return the same 48,256 byte variable font. Shipping that
file twice under two names would have cost 96,512 bytes for what one file does,
and shipping it once under a name that claims a single weight would have been
misleading.

Instead the variable file was instanced to two static weights with `fontTools`
(`instantiateVariableFont` at `wght=400` and `wght=600`), which is why the two
Inter files are 23.7 KB and 24.4 KB rather than 48.3 KB each. The saving against
the naive approach is 48.3 KB, and it is the difference between 88 KB and
136 KB against a 140 KB budget.

`fontTools` and `brotli` were installed into the local Python environment as
build tools. Nothing was added to `package.json`, no `npm install` was run, and
neither library is a runtime dependency of the site. Only the four `.woff2`
outputs are committed.

## 3. Metric overrides: method and numbers

`font-display: optional` is on all four faces, per spec 5.3. That is the value
that makes the CLS budget of exactly 0.00 achievable: the font is either ready
inside the block period or the fallback is used for the whole page life. There
is never a swap, so there is never a second layout.

The metric overrides therefore are not there to prevent a mid-load shift (there
cannot be one). They are there so that a cached load and an uncached load
produce the **same** layout: the same line breaks, the same block heights, the
same section positions.

### Method

Two stages, both in headless Chromium (Playwright 1.63.0, Chrome Headless Shell
153), on Windows 11.

**Stage 1, seed, canvas.** Each webfont was registered through the `FontFace`
API with no overrides, so its raw metrics were readable. A 130 character Latin
corpus was measured with `measureText` at 1000px in both the webfont and its
fallback stack, and `measureText('Hxp').fontBoundingBoxAscent/Descent` gave each
font's used ascent and descent. Then:

```
size-adjust      = fallbackAdvanceWidth / webfontAdvanceWidth
ascent-override  = (fallbackAscent  / em) / size-adjust
descent-override = (fallbackDescent / em) / size-adjust
```

The division by `size-adjust` is required because `size-adjust` scales the
overridden metrics too, so the override has to be pre-divided to land on the
fallback's value.

**Stage 2, refinement, real DOM.** The stage 1 values were written into
`base.css`, then the same corpus was laid out in actual DOM spans at 1000px with
`line-height: normal`, and the residual was folded back in. This stage matters:
canvas and DOM disagreed by up to 1.8% on advance width, because `body` sets
`text-rendering: optimizeLegibility` and the resulting kerning behavior differs
between the webfont and the fallback. DOM layout is what decides line breaks, so
DOM is the measurement that counts.

Verification ran against a copy of `base.css` with `font-display` switched to
`block`, because `optional` correctly refuses to use the webfont on an uncached
load and there would otherwise be nothing to measure.

| Family | advance width delta vs fallback | line box height delta vs fallback |

### Platform caveat, stated plainly

These are Windows/Chromium fallback metrics. `-apple-system` on macOS resolves
to San Francisco, not Segoe UI, and San Francisco has different metrics, so the
Inter overrides are tuned slightly off for a macOS visitor whose first load is
uncached. This is inherent to a single-value override against a multi-platform
fallback stack and there is no CSS mechanism to vary it per platform. The choice
of platform to tune against was made on measurement availability, and it is
recorded here rather than hidden. It does not affect CLS on any platform,
because `font-display: optional` never swaps.

## 4. Spec challenge: the Instrument Serif size-adjust

Recorded also as a one-line entry under `## Spec challenges` in `PROGRESS.md`.

Instrument Serif is an intrinsically narrow display serif: at the same nominal
size it sets about 26% narrower than Georgia while its cap height is within 2%
of Georgia's. Matching its advance width to Georgia therefore requires
`size-adjust: 135.09%`, and that scales its cap height to roughly 138% of
Georgia's.

The consequence, precisely: layout is identical between a cached and an uncached
load (that is the whole point, and it is verified above), but the hero headline
**looks** noticeably larger on a cached load than the Georgia fallback does on
an uncached one. Same box, different apparent type size.

This is the direct result of following spec 5.3, which puts the overrides on the
webfont's own `@font-face`, measured against the fallback. That direction makes
the webfont match the fallback. The alternative industry pattern (the one
`fontaine` and `next/font` use) inverts it: declare a separate adjusted fallback
family backed by `src: local('Georgia')` and make the **fallback** match the
webfont, which preserves the display face's intended proportions. That was not
built, because it changes the font stack tokens that WP-05 and every section
package now consume, and this package does not own those consumers.

**If the orchestrator or WP-09a wants the display face at its design
proportions, the one-line change is in `base.css`, Instrument Serif block:**

```css
size-adjust: 100%;
ascent-override: 91.70%;   /* Georgia's measured ascent  */
descent-override: 21.90%;  /* Georgia's measured descent */
```

That keeps the line box matched to Georgia (so block heights still agree) and
gives up only advance-width agreement, which with `font-display: optional`
affects line wrapping between a cold and a warm load, never within one load.
CLS stays 0.00 either way. Shipping the measured value as specified, and
flagging the trade rather than deciding it unilaterally.

## 6. Other decisions

- **`--bp-*` shipped as tokens.** Spec 5.4 defines them and says they exist for
  documentation and for JS `matchMedia` strings. They are in `tokens.css` with a
  comment stating that stylesheets must write the literal px value, since a
  custom property cannot appear in a media query condition.
- **Reveal primitives.** `.reveal` at `opacity: 0; translateY(14px)`,
  `.is-revealed` settled with `transition: opacity 600ms var(--ez-out-expo),
  transform 600ms var(--ez-out-expo)`. `.no-motion .reveal` and
  `.no-motion .is-revealed` both settle with `transition: none`, at specificity
  (0,2,0) so the no-motion pair wins without `!important`. The
  `prefers-reduced-motion` block settles `.reveal` independently of JS and zeroes
  transition and animation durations globally, so the contract holds even if the
  WP-03 class is never applied.
- **`scroll-behavior: smooth`** on `html`, reverted to `auto` under
  `prefers-reduced-motion`.
- **`section[id] { scroll-margin-top: 80px }`** per spec 4.0, so anchor targets
  clear the fixed 64px header.
- **Never justify** is enforced as an explicit `text-align: left` on the text
  elements rather than left as a default, so a later `text-align: justify`
  somewhere has to be deliberate.
- **`:focus:not(:focus-visible) { outline: none }`** is the one `:not()` in the
  file. Spec 18.3 bans `:not()` chains for styling; this is a single-argument
  reset of a UA default at specificity (0,2,0), not a chain used to target
  content.
